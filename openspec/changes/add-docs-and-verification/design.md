## Context

Every prior change proved something with a test only someone running this repo would ever see.
This change is the one meant to be read, not run — a reviewer's actual path through the assignment
is almost certainly README first, code second. What it says has to be accurate on the day it is
read, not on the day `add-project-foundation` was archived.

## Decisions

### Examples come from a real run against real tools, with only the model scripted

**Chosen:** `scripts/generate-examples.ts` calls `executeRun` for each of the six seeded
business-case messages, exactly as `run.spec.ts` and `injection.spec.ts` already do in Jest, using
`scriptedModel` to stand in for the parts of a real model's behaviour this project cannot pin down
(which tool it calls, in what order, and its own prose) — never for `check_ad_policy`,
`search_rate_card` or `calculate_quote`, whose real seeded data and real arithmetic run exactly as
they would for a live call. The script writes each run's message, trace and assessment to a
Markdown file under `examples/`.

**Alternatives considered:**

- A live run against a real model, captured once and committed. Rejected: it would need a paid API
  key at generation time, could not be regenerated by a reviewer without one, and a real model's
  prose is exactly the part of a run this project's own test suite deliberately does not assert on
  (`.claude/rules/testing.md` rule 8) — an example that could vary between generations is a worse
  teaching tool than one that cannot.
- Hand-written example transcripts, not generated at all. Rejected: hand-written output could
  silently drift from what the code actually does, which is the exact failure mode a take-home
  reviewer is likely to catch and penalise — an example is only worth committing if generating it
  again reproduces it.

**Deterministic check:** every generated example's quote total, policy decision or refusal reason
is read directly off the `RunStep` rows `executeRun` wrote for that run, not composed by the
generator script — the same discipline `checkPostConditions` already holds the agent itself to.

### The script is a one-off generator, not a test

**Chosen:** `scripts/generate-examples.ts` is invoked by hand (`npm run examples:generate`) against
its own disposable, freshly migrated-and-seeded SQLite file — built the same way
`jest.globalSetup.ts` builds its test-database template — and its output is committed like any
other source file, not regenerated on every `npm test` run.

**Alternatives considered:** a Jest test that writes `examples/*.md` as a side effect of running.
Rejected: `.claude/rules/testing.md` rule 1 scopes Jest to proving behaviour, and a spec whose job
is to mutate tracked files on disk is doing something a reviewer running `npm test` would not
expect a test to do — regenerating documentation is a deliberate, visible act, not something that
should happen quietly inside a green test run.

## Risks

- **Examples can go stale.** Nothing fails CI if `examples/` drifts from what the current code
  would actually produce, since regeneration is manual. Acceptable for a take-home whose codebase
  is finished, not under active development; a real project would gate this in CI once there is a
  CI to gate it in.
- **The `npm run e2e` single-dev-server gotcha is documented, not fixed.** It is a Next.js 16
  platform behaviour (one dev server per project directory, independent of port), not a defect in
  this project's Cypress or `start-server-and-test` configuration — reproducible only by a
  developer who deliberately runs a second `next dev` on a non-default port while `npm run e2e` is
  also trying to start one on port 3000, which the documented setup commands never do on their own.
  Naming it in the README costs a sentence; building detection tooling for a scenario the
  documented workflow cannot produce would not.

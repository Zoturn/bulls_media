# project-verification Specification

## Purpose
Makes what the project already proves in tests legible to a reviewer who only reads: a committed,
reproducible worked example per business case, and a README accurate enough that following its
documented commands reproduces a clean pass.
## Requirements
### Requirement: Every business case has a committed, reproducible worked example

The project SHALL commit one worked example per row of the README's "Business cases covered"
table, generated by running the real orchestrator and its real deterministic tools against the
corresponding seeded message. Each example MUST show the inbound message, the step-by-step trace
of what the tools actually returned, and the resulting assessment.

#### Scenario: A reviewer reads an example without running anything

- **WHEN** a reviewer opens a file under `examples/`
- **THEN** it shows the seeded message it was generated from, every tool call and result in the
  trace, and the final disposition, summary and (when present) quote or refusal reason — with
  nothing left for the reviewer to run to see what the case produces

#### Scenario: An example's tool results come from the real engines, not a script

- **WHEN** the example generator runs a case through `executeRun`
- **THEN** `check_ad_policy`, `search_rate_card` and `calculate_quote` execute against the real
  seeded rate card and policy table, and only the model's own tool-selection order and prose are
  supplied by a scripted model — an example's quote total or refusal reason is real output, never
  a value the generator invented to match the README's own claims

#### Scenario: The examples are regenerated deliberately, not automatically

- **WHEN** the seeded fixtures or the orchestrator's behaviour changes
- **THEN** `examples/` is stale until someone runs `npm run examples:generate` and commits the
  result, so a diff in `examples/` is a visible, reviewed fact about a change rather than build
  output nobody looked at

### Requirement: The README states current status and how to verify every claim it makes

The README SHALL accurately reflect which OpenSpec changes are complete, MUST document every
command a reviewer needs to reproduce a clean verification pass, and MUST name any limitation
discovered while finishing the project that would otherwise cost a reviewer time to diagnose
themselves.

#### Scenario: A reviewer follows the documented commands on a clean checkout

- **WHEN** a reviewer runs the commands the README's "How to test and verify" section lists, in
  order, on a machine with nothing else of this project running
- **THEN** every command succeeds exactly as documented, with no undocumented manual step required

#### Scenario: A known environment gotcha is named, not left for a reviewer to diagnose

- **WHEN** the README documents `npm run e2e`
- **THEN** it states that Next.js allows only one `next dev` per project directory regardless of
  port, so a dev server already running on a different port for this project will make `npm run
e2e`'s own server fail to start, and says what to do about it
